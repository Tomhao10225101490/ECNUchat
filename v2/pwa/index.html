ECNUchat v2 PWA

Relay mode uses real X3DH + double ratchet (tweetnacl + WebCrypto), hybrid PQXDH + hybrid ratchet (ML-KEM-768) when both sides hold PQ keys — keys live in localStorage (not production-grade secure storage), and this is NOT a production messenger. Local demo mode is a separate stand-in and every demo message is tagged DEMO-NOT-E2EE-REAL. Do not use either mode for real private messages. See README.md and the “Not implemented” section at the bottom.

1 · Identity — register locally

Username rule (same as v1): 3–20 characters, letters, digits, underscore only. Identity is username:device. A lost device means a lost identity — there is no recovery in this scaffold (see README).

No identity yet. Register above.

Key store: keys/fingerprint are kept in localStorage under a key starting ecnu-chat-v2. This is explicitly not production-grade secure storage (no hardware keystore, no OS keychain, readable by any script on this origin). Production must move keys to a proper secure store. Note: an older demo store under ecnu-chat-v2-demo is NOT migrated; re-registering here creates a new identity.

2 · Friends — add by invite

Paste an invite: either JSON {"username":"bob","device":"phone","relay":"http://127.0.0.1:8765","fingerprint":"…"}, or lines: username, relay URL, fingerprint, [device]. Fingerprint is shown for out-of-band comparison; this client does not verify it cryptographically (stub). In relay mode, friend devices are then fetched from the relay's device directory.

    Device fan-out: sending delivers one envelope per registered device of the friend (see fan-out log in chat). In relay mode, devices come from the relay directory; a friend with no registered devices cannot receive until they register.

    3 · Chat — 1-to-1 text only

    Demo peer tab opens this page with ?profile=peer, which uses a separate localStorage namespace so two tabs can act as two users and exchange envelopes over BroadcastChannel. Without a second tab, use “Simulate friend reply” (local echo).

    Not implemented — stubs / absent, not claimed as done

    • Real X3DH + double ratchet (classical): IMPLEMENTED in relay mode (crypto.js, tweetnacl + WebCrypto, x3dh-v1 / dr-v1). Demo mode still uses a stand-in and is tagged as such.
    • ML-KEM-768 (post-quantum hybrid): IMPLEMENTED in relay mode (crypto-pq.js, vendored noble ML-KEM-768, PQXDH + hybrid ratchet). A session is hybrid iff both sides hold a PQ key; a PQ peer refuses a classical initial (no silent downgrade) and a no-PQ peer stays classical (never upgraded to hybrid). Sessions with a no-PQ peer are classical, not post-quantum.
    • Interop with the original Python v1 client: NOT TESTED and NOT CLAIMED. Crypto primitives, KDF labels and ratchet payload field names match v1, but v1's transport is WebSocket (not this HTTP relay) and its bundle store format differs; a bridge/adapter would be needed and has not been built.
    • Groups, voice, push notifications, backup/restore, device endorsement: absent (no UI, no protocol in this client). Device revocation is relay-side only (see relay README); this client has no revoke button yet.
    • Fingerprint verification, sealed sender, WebSocket transport, TLS: stub/absent. Fingerprint is displayed only; the relay sees sender/recipient metadata; the local relay is plain HTTP on loopback only.
